# Milestone 10 — Hand cages

Added 2026-11-24. Branch: `feat/m10-hand-cages`, from `main` (9.5 merged).

## Goal

For each hand, show a translucent **cage** over the keys that hand covers in each bar, so the player can see hand positions and shifts ahead of time. Cages are computed once from the song and drawn on the highway, behind the notes.

## Housekeeping first (from 9.5)

2. **The flaky Welcome highlight test.** `@welcome highlights rotate every 8 s` uses the fake clock: make it deterministic.

## Reference: the Unity behaviour (what we're porting)

When a song loads, the Unity app computes one range per channel per bar:
- The cage is the lowest → highest pitch of the notes that start in the bar.
- A bar with no notes reuses the previous bar's range.
- A range narrower than 5 semitones is widened to 5, toward where the hand came from: hand moved down → widen up; moved up → widen down; no movement or first bar → centred.
- It's drawn from half a key below the low note to half a key above the high note.

This milestone keeps that model and fixes its gaps (see "Intentional differences").

## Definitions

- **Hand:** right or left. **Every note's hand comes from one function, `handOf(note)`.**
  - Today it reads the song's existing channel → hand assignment (Right / Left / Hidden, in the Library details). Several channels may map to one hand; their notes are merged.
  - Milestone 10.5 (hand detection and split) will replace it with a per-note assignment.
  - **Cages must depend only on `handOf`, never on channels directly**, so 10.5 plugs in without touching the cage code.
  - Notes whose hand is Hidden belong to no hand and make no cage.
- **Bar:** the span [barStart, nextBarStart) in ticks, from the song's bar map.
- **Sounding in a bar:** a note with start < barEnd and end > barStart. Zero-length notes count as end = start + 1.
- **Spread:** high − low in semitones.
- **Cage:** the pitch range one hand covers in one bar.

## Data model (core, pure)

```ts
type Hand = 'right' | 'left'

interface HandCage {
  barIndex: number
  startTick: number   // this bar's start
  endTick: number     // this bar's end
  low: number         // MIDI pitch, inclusive
  high: number        // MIDI pitch, inclusive
  carried: boolean    // copied from the previous bar (no notes sounding)
}

type HandCages = Record<Hand, HandCage[]> // ordered by barIndex; bars without a cage are omitted
```

Constants, in the render model (not settings): `MIN_CAGE_SPREAD = 5`, `PIANO_LOW = 21`, `PIANO_HIGH = 108`.

## Algorithm: `computeHandCages(notes, barMap, handOf): HandCages`

Pure and deterministic. For each hand, walk the bars in order, keeping the previous bar's final cage (`prev`):

1. **Collect** the hand's notes sounding in the bar.
2. **Range:**
   - Notes found: low = min(pitch), high = max(pitch), carried = false.
   - No notes, and `prev` exists: copy `prev.low` and `prev.high`, carried = true.
   - No notes and no `prev` (leading rests before the hand's first note): no cage for this bar.
   - **After the hand's last note: no more cages.** Trailing rests don't carry.
3. **Minimum height:** while spread < 5, widen one semitone at a time:
   - `prev` exists and mean(prev) > mean(current) (hand moved down): raise high.
   - `prev` exists and mean(prev) < mean(current) (hand moved up): lower low.
   - Otherwise (no `prev`, or equal means): centred. Alternate raise high / lower low, starting with high.
   - Clamp to [21, 108]. If the preferred side is clamped, widen the other side instead.
   - mean = (low + high) / 2 as a float, compared against `prev` after prev's own widening.
4. **Timing:** `startTick` and `endTick` are always this bar's boundaries, carried cages included.
5. **Emit** the cage; it becomes `prev`.

Recompute on song load and on a change to the hand assignment, nothing else. Tempo, seek, loops and pre-roll never change cages.

## Rendering

1. **Reuse the 9.x cage renderer** (`CageLayer`, `CageRegion`, `setRegions()`, built in milestone 9 for exactly this), with the same fills, stripes, borders, glow, corner rounding and the `NoteMask` stencil, so a cage never tints a note.
2. **Horizontal extent:** from the outer edge of the low key's lane to the outer edge of the high key's lane, using **the same key layout as the notes and keyboard**, never a separate pitch → position formula. That's the half key either side.
3. **Depth extent:** bar start to end, using the same tick → position mapping as the notes.
4. **Joined bars:** consecutive cages of one hand with the same low and high (carried or not) draw as **one region**, with no border line between them (`CageRegion` open ends). A change of range starts a new region.
5. **Carried bars** (rests holding the last position) draw at reduced strength: setting "Carried bars", default 50 % of the cage's fill and border. That shows "the hand is resting here" without claiming notes.
6. **Order:** the pedal cage, then the hand cages, then the notes. Lines stay over cages, as with the pedal cage today.
7. **Loops and playlists:**
   - Hand cages are dimmed outside the loop (9.2 `loopDim`) and repeated in "Next repeat".
   - In listening mode they follow each song segment of the merged timeline, and the ending song's cages dim through the crossfade band like its notes.
8. **Visibility is decided at render time,** so the toggles apply at once without recomputing or rebuilding.
9. **Performance:** build the geometry once per song and assignment (instanced or merged), and draw only cages in the visible window. Report draw calls with cages on and off, at Off and Medium.

## Tests

**Unit** (`computeHandCages`, pure, run locally):
- A bar whose notes span ≥ 5 semitones: exact low and high, no widening.
- A narrow first bar: centred widening to a spread of 5, starting with high.
- The hand moves down into a narrow bar: high raised.
- The hand moves up into a narrow bar: low lowered.
- A rest bar after notes: the carried range, `carried: true`, with the rest bar's own start and end.
- Several rest bars in a row: each carries the same range, and the spread doesn't grow.
- Leading rest bars before the first note: no cages.
- Trailing rests after the last note: no cages.
- A note sustained across a bar line: counted in both bars.
- A note ending exactly on a bar start: not counted in that bar.
- A narrow range at the keyboard ends (near 21 or 108): clamped and widened on the free side.
- A time-signature change: cage widths follow the real bar boundaries.
- Two channels mapped to one hand: notes merged. A change of assignment recomputes.
- A Hidden channel makes no cage. A hand with no notes gets an empty list.
- **Region joining:** equal consecutive cages make one region; a range change splits it.

**E2e** (`@cages` tag, via `test:e2e:affected`):
- Cages appear for both hands, behind the notes.
- Toggling global and per-hand visibility applies at once.
- A change of hand assignment in the Library updates the cages.

**Contact sheet** (`docs/design/m10/`): a song with rests, sustained notes and a meter change; 25°, 35° and 85°; quality Off and Medium; Classic with cages on, plus two looks; carried bars visible; a loop with Next repeat.

## Acceptance criteria

- Cages for both hands on bundled songs and uploads, aligned exactly with the key lanes and bar lines.
- Sustained notes widen the bars they sound in. Rest bars hold the previous position at the correct length, dimmed. Nothing after a hand's last note.
- A change of hand assignment updates the cages; tempo, seek and loops don't.
- The toggles take effect at once and persist (and are part of looks).
- No drawing over notes; no z-fighting with the pedal cage.
- Draw calls with cages on are reported; the cost on tablets goes on the milestone-11 list.

## Intentional differences from Unity

| Unity                                       | This milestone                                      | Why                                          |
| ------------------------------------------- | --------------------------------------------------- | -------------------------------------------- |
| Only notes starting in a bar count          | Notes sounding in a bar count                       | Held notes are part of the hand position     |
| Carried cages keep the previous bar's timing | Carried cages use the current bar's timing          | Correct width after time-signature changes   |
| Carry to the end of the song                | Stop after the hand's last note                     | No phantom cages                             |
| Carried cages look the same                 | Carried cages are dimmed                            | Rest vs. playing is visible                  |
| Clamp to MIDI 0–127                         | Clamp to the piano, 21–108                          | The app always shows the 88 keys             |
| Heights from a scaling factor               | Extents from the shared key layout                  | Cages can't drift from the keys              |
| Visibility fixed at build time              | Visibility checked at render time                   | Toggles apply at once                        |
| Hand from the channel                       | Hand from `handOf(note)`                            | Ready for per-note assignment in 10.5        |

## Open questions, decided

1. **Trailing rests:** stop after the last note.
2. **Long rests mid-song:** carry indefinitely in v1, but dimmed ("Carried bars"). Revisit after use.
3. **Toggles:** one global plus per hand.
4. **Muted or soloed hands:** cages unchanged (mute and solo are audio). A **Hidden** hand has no cage.
